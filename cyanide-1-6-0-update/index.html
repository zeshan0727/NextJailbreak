Cyanide 1.6.0 Focuses on Navigation, Kernel Session Handling, and Safer Reads

Cyanide 1.6.0 is a maintenance release for the Kolbicz-maintained iOS tweak runner. The project configuration moves from version 1.5.9 to 1.6.0 and raises the internal build number from 1005009 to 1006000. Rather than expanding the documented compatibility range, the release concentrates on Settings navigation, preservation of kernel read/write access during backgrounding and sleep, and preventing read-only settings actions from starting a new exploit chain. The release also keeps an unconfirmed SpringBoard main-thread experiment out of the released line.

Key points

  • Cyanide 1.6.0 changes the configured marketing version from 1.5.9 to 1.6.0 and the build number to 1006000.
  • Settings navigation now waits for the relevant controller to disappear before unwinding its navigation stack.
  • Kernel read/write access can remain parked with launchd during backgrounding, while foregrounding no longer eagerly reattaches it.
  • Read-only actions can recover an existing session but will not launch a fresh exploit chain when no usable session is available.
  • The released line does not include the experimental SpringBoard main-thread change from the 1.5.9 test build.
  • The documented target range remains iOS/iPadOS 17.0–18.7.1 and 26.0–26.0.1, with several explicit version and hardware exclusions.

A reliability-focused release rather than a compatibility expansion

The official project metadata describes Cyanide as an iOS tweak runner for kernel research, focused on Kolbicz-maintained tweaks and built on the DarkSword kernel primitive. Its README explains that supported tweaks are applied in memory for the current boot instead of turning the device into a conventional, persistent jailbreak environment.

Cyanide 1.6.0 changes the project configuration from marketing version 1.5.9 to 1.6.0 and increases the internal build number from 1005009 to 1006000. The accompanying source changes are primarily concerned with reliability: the behavior of navigation controllers, the lifetime of kernel read/write access, and the distinction between reading a setting and acquiring a new kernel session.

The release should therefore be viewed as an operational update for existing supported users. The supplied material does not describe a newly supported operating-system window or a new device family. Compatibility remains governed by the ranges and exclusions in the current README.

Settings navigation moves cleanup to viewDidDisappear

One of the clearest user-facing changes concerns the return path from package or tweak details to the Installer tab. The recent commit explains that earlier implementations tried to pop the Settings navigation stack before the tab switch, after the switch, or after deferring the pop by one run-loop turn. Those approaches produced different results across operating-system versions, including the referenced observations on iOS 17.2, iOS 18.5, and iOS 26.3.

The new implementation switches tabs and sets a flag indicating that the Settings stack should later be unwound. The actual pop occurs from viewDidDisappear, after UIKit reports that the controller has left the visible hierarchy. A guard flag is important here: viewDidDisappear can also run when another controller is pushed over the current one, and unwinding the stack in that situation would be premature.

If no Installer tab is available, the code uses an immediate pop as a fallback. The intended result is to avoid briefly displaying the Settings root or an intermediate Quick Actions or Tweaks screen during the transition, while still ensuring that a later visit to Settings does not reopen the previous package-control screen. The supplied commit documents the design and the earlier version-dependent observations; it does not establish a blanket on-device confirmation across every referenced scenario.

Kernel access is parked more selectively during backgrounding

Several changes revise the handling of Cyanide’s kernel read/write session, called KRW in the source. When the application moves into the background, Cyanide can detach the relevant sockets to launchd so the primitive can survive device sleep. Version 1.6.0 adds a check for whether that handoff is useful at the time it is requested.

The new idle check declines to park the session when a registered live tweak loop is running or when a persistent SpringBoard RemoteCall user still needs the session attached to the app. The source explains that a live loop may reattach the session on its next cycle, so repeatedly detaching and reattaching during active work would create unnecessary churn. If the session has already been detached, the later background path recognizes that state instead of attempting another handoff.

Foreground behavior is also less eager. Cyanide no longer automatically pulls the kernel-session file descriptors back into the application as soon as the app becomes active. The session can remain with launchd, and the next kernel access recreates the descriptors when needed. The stated purpose is to avoid returning the primitive to the app without an immediate request for it.

This change concerns the availability and coordination of kernel access, not the persistence of every tweak. The README says ordinary tweaks are applied in memory for the current boot and that a respring undoes them. Individual system entries may have their own persistence descriptions, so users should evaluate those entries separately rather than treating the session changes as a promise that modifications survive every reboot or respring.

Read-only actions no longer launch a fresh exploit chain

Cyanide 1.6.0 introduces a separate path for read-only settings operations. It first checks whether the device is supported, then looks for an already active kernel session or attempts to recover a session that was parked. If neither is available, the read-only path returns without starting a new exploit chain.

The source identifies this behavior in several settings-related callers, including reading the lock-screen duration, checking OTA status, and running the Nano probe. Updated log messages distinguish the absence of kernel access from an exploit failure and explicitly state that a read-only action will not re-exploit on its own.

This separation makes the behavior of settings screens more predictable. Tapping a control that only reads a current value should not unexpectedly trigger the same acquisition process as an explicit kernel or exploit action. Users should still expect that operations requiring kernel access may need the chain to have been run previously, or that a parked session must be recoverable.

The experimental SpringBoard threading change is not in the release

The recent history records a deliberate revert involving SpringBoard view-hierarchy access. A previous experimental change moved repeated view walks onto SpringBoard’s main thread. Its comments associated off-main-thread access with races involving live UIKit hierarchy handling and possible SpringBoard crashes.

The maintainer’s revert states that this change appeared only in the v1.5.9-test1 pre-release and had not been verified on a device. It was therefore removed from the released line so the main tree matched the v1.6.0 release state. The experimental implementation remains preserved separately for possible future confirmation.

That distinction is important when assessing 1.6.0. The release includes the navigation lifecycle change described above, but readers should not assume that it also includes the experimental main-thread implementation or that the source has conclusively resolved every reported SpringBoard stability scenario.

Compatibility remains tightly version- and hardware-dependent

The current README lists iPhone and iPad support for iOS/iPadOS 17.0 through 18.7.1 and 26.0 through 26.0.1. It excludes iOS 16.x and earlier, versions 18.7.2 through 25.x, and version 26.1 or later. The README attributes the later-version cutoff to fixes for the kernel bugs used by the project.

Within the supported version windows, the project says it does not use a separate device whitelist. It describes offset scanning that handles older A-series hardware through A18, as well as M-series iPads. The README lists confirmed working examples including an iPhone 16 Pro Max on iOS 18.5, an iPhone 15 Pro Max on iOS 17.3.1, and an M-series iPad.

The iPhone 17 family, identified as A19 or A19 Pro hardware, and M5 devices are listed as unsupported because Memory Integrity Enforcement blocks the exploit. The README says these models are refused by identifier so users receive a clear unsupported-device message instead of proceeding to a failed exploit attempt.

The gaps in the supported range make the exact installed build important. A device running a nearby version is not necessarily supported, particularly because the README explicitly excludes the entire 18.7.2–25.x range.

What users should review before installing

Cyanide’s tweaks are installed through the in-app Installer and, according to the README, are generally applied in memory for the current boot. The collection includes Home Screen, SpringBoard, Status Bar, theming, and system features. It also includes beta entries that may produce SpringBoard glitches, crashes, partial behavior, or a need to reapply changes between builds.

Some entries have consequences beyond visual customization. The documented collection includes controls related to OTA updates, watch pairing, location simulation, and call-recording disclosure sounds. The README warns that simulated locations may conflict with app terms, game rules, ride-share or delivery policies, platform rules, or local law. It also notes that disclosure sounds may be legally required depending on where the user lives.

The project is maintained primarily around Kolbicz-based tweaks and does not provide support for tweaks outside that maintenance scope. Users should prioritize the current README over archived project material, verify the exact operating-system build and hardware model, and read the documentation for each intended tweak rather than generalizing from Cyanide’s normal in-memory behavior.

Frequently asked questions

What is new in Cyanide 1.6.0?

The project changes from version 1.5.9 to 1.6.0 and focuses on reliability. Changes include lifecycle-based Settings navigation cleanup, more selective parking of kernel access with launchd, lazy recovery of that access when needed, and read-only actions that refuse to start a fresh exploit chain.

Does Cyanide 1.6.0 expand device compatibility?

The supplied official material does not describe expanded compatibility. The documented range remains iOS/iPadOS 17.0–18.7.1 and 26.0–26.0.1. iOS 16.x and earlier, 18.7.2–25.x, 26.1 and later, the iPhone 17 family, and M5 hardware are listed as unsupported.

Will Cyanide tweaks survive a reboot?

Not generally. The README says tweaks are applied in memory for the current boot and that a respring undoes them. Some individual system entries have separate persistence descriptions, so users should check the documentation for the specific tweak.

Does the released version include the experimental SpringBoard main-thread fix?

No. The recent commit explicitly reverts that change from the released line because it appeared only in a test pre-release and had not been verified on-device. The experimental implementation remains preserved separately for possible future work.

What should users check before installing?

Check the exact iOS or iPadOS build, device model, and whether the intended tweak is stable or beta. Also review warnings for location simulation, call-recording disclosure sounds, OTA behavior, and watch pairing. Use the current official project materials and packages.

Before installing: confirm the current package version, compatibility and dependencies at the original developer/repository source for your exact device and jailbreak.
