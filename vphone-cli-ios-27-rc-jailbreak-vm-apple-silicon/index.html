How to Update vphone-cli 2.15.2 Safely on Apple Silicon

Move an existing 2.14 installation to the current 2.15 series without erasing guests, or create a new research VM with the correct Launchpad, Core Bundle and firmware pair. This guide separates host fixes from guest updates and explains the new RootHide/rootless bootstrap option.

By Zeeshan Barvi · Originally published September 15, 2026 · Updated November 6, 2026

Current version: vphone 2.15.2, released November 3, 2026. SHA-256: d43af99a3cbf4e8fe7268cb4ecdde78cadae4302d064887dd6b3fb3f32f971bf for VPhone-2.15.2.zip and 596ab763f68ec86ed01f5557daeb3e4e5b8df9e3a556134b60e93461d7d0a499 for Launchpad 2.15.2.
This is not a physical-device jailbreak. vphone creates patched research guests on a Mac. RootHide, rootless or iOS support inside a VM does not prove a retail iPhone is jailbreakable.

What the 2.15 series adds

Version 2.15.0 introduced HomeView guests, native OpenGL ES, iPhone Duo automation, first-boot RootHide or rootless package environments and a service-profile correction for high idle CPU. Version 2.15.1 then fixed regression findings across six Macs: iOS 18 standard guests, Apple TV/HomePod device.info delays, iPhone Duo cfw install memory use, GLES rendering and minimal/watchOS boot patches.

Version 2.15.2 is a localization and documentation release. It completes Japanese, Korean, Vietnamese and Simplified Chinese coverage, separates ambiguous UI strings, corrects the default NAT subnet and reorganizes the guides. The project says Launchpad and VPhone.bundle behavior is unchanged from 2.15.1.

Requirements before you start

Requirements before you start

  • A physical Apple Silicon Mac running macOS 15 or later. The official host guide says PV=3 guests do not run inside a nested macOS VM.
  • Administrative access and a recovery plan. vphone’s private virtualization entitlement requires changing host security policy. Back up the Mac and understand how to restore its previous SIP and boot-argument state.
  • Enough storage and memory. A new VM defaults to a 64 GB virtual disk, 8 CPU cores and 8192 MB of memory. Prepared firmware and caches consume additional space.
  • Two compatible firmware inputs: an iPhone restore IPSW and a PCC/cloudOS IPSW listed as a verified or supported pairing by the project.
  • Network access during creation for Apple restore tickets and any firmware downloads.

1. Download the correct 2.15 files

VPhone-2.15.2.zip is the current Core Bundle. The current Launchpad is CI-built and not notarized, so macOS blocks it the first time it opens. If you prefer notarization, official Launchpad 2.15.0 remains compatible with bundle 2.15.2; the 2.15 series is interchangeable and the minimum bundle remains 2.15.0.

2. Update an existing VM without erasing it

  1. Stop important VMs and create a snapshot, clone or export.
  2. Install a 2.15 Launchpad and 2.15.2 Core Bundle together; Launchpad 2.15 cannot use a 2.14 bundle.
  3. Keep the old 2.14 bundle, bind one stopped test VM to 2.15.2 and start it.
  4. Expect new templates: 2.14 templates are not reused because the series is part of the template key.
  5. Use environment or kernel updates only when the desired feature needs guest-side components.
  6. Remove 2.14 only after every machine starts, stops and reports device.info.

3. Prepare the Mac’s host policy

3. Prepare the Mac’s host policy

Both supported policy paths require csrutil allow-research-guests enable from macOS Recovery. The official host guide then offers two choices:

  • More permissive: disable SIP and AMFI using the documented Recovery and boot-argument commands.
  • More restrictive: keep SIP enabled with debugging restrictions relaxed, then use the bundled vphone-escalator helper to allowlist the current signed vphone-vm.

Prefer the more restrictive route when it works for your setup. Do not paste a replacement nvram boot-args value without first recording existing boot arguments; replacing that variable can remove unrelated settings. The allowlist is tied to the signed build’s cdhash, so the official guide says to repeat the allow command after every rebuild or signature change.

After installing the official bundle, run:

vphone-cli host preflight

If AMFI refuses the entitled companion, preflight prints the exact helper command for that installed bundle. Use that path rather than copying a command that points at someone else’s build directory.

4. Select a verified firmware pair

Start with the project’s live catalogue:

vphone-cli fw catalog

The simple path in the official guide uses an iPhone17,3 restore IPSW with a compatible PCC/cloudOS IPSW. The project’s compatibility table records combinations that actually reached the guest and answered a vphoned ping; it explicitly warns that other pairings may be untested.

Do not infer compatibility from matching version numbers alone. Recent cloudOS releases may lack the vphone600 components used by the older direct path, and some combinations require a research-board kernelcache recipe or a different macOS linker layout. If the catalogue refuses a pairing, choose a listed combination rather than forcing the restore.

5. Create the virtual iPhone

With the two firmware files stored locally, the official one-command flow is:

vphone-cli host preflight
vphone-cli vm create myphone \
  --iphone-source /path/to/iPhone_Restore.ipsw \
  --cloudos-source /path/to/cloudOS.ipsw

The pipeline performs preparation, firmware patching, an online DFU restore, host-mounted custom-firmware installation and a first GUI boot. Root privileges are required for the CFW installation stage; inspect the executable path and follow the official prompt rather than running unrelated scripts with sudo.

By default, current versions build a reusable template and clone the named VM from it. A later VM with the same device, firmware, preset and disk settings can clone that template instead of restoring again. Omit --keep-artifacts unless you deliberately need the large prepared restore tree.

6. Start the VM after creation

A successful creation ends after vphoned answers during the verification boot, then the verification VM stops. That is expected. Start the guest explicitly:

vphone-cli vm launch myphone

Stop it from another Terminal window with:

vphone-cli vm stop myphone

Closing the window, quitting the app or interrupting the launch command first asks the guest to shut down. The VM window provides Home and power keys, app installation and file browsing.

Create a RootHide or rootless research guest

vphone-cli vm create myphone \
  --iphone-source /path/to/iPhone_Restore.ipsw \
  --cloudos-source /path/to/cloudOS.ipsw \
  --bootstrap roothide

Use rootless instead for the conventional rootless route. The official 2.15.0 release says this installs Irisin and owngoal-bootstrap-vphone during first boot, then shuts down. Irisin 5.1.5 or later is required; Apple TV skips package installation. This is a new-guest VM option, not a physical jailbreak or a documented retrofit for an existing guest.

For physical-device migration, follow the separate RootHide guide. For released jailbreak availability, check the Dopamine 3 compatibility guide.

Corrected NAT subnet

Version 2.15.2 corrects the subnet named by vm config --help and --ip errors. NAT guests use 192.168.65.0/24 by default, or 192.168.64.0/24 with --nat-peers off.

Troubleshooting checklist

  1. Bundle too old: install a 2.15-series bundle; Launchpad 2.15 has 2.15.0 as its minimum.
  2. macOS blocks Launchpad: 2.15.2 is officially non-notarized. Verify the hash and use Open Anyway, or use notarized 2.15.0 with bundle 2.15.2.
  3. Old template is not reused: expected when moving from 2.14 to 2.15.
  4. OpenGL ES still fails: binding alone may not replace the guest compiler plugin or kernel patch.
  5. Apple TV/HomePod times out: boot with 2.15.1 or later and retry after automatic vphoned deployment.
  6. iPhone Duo install exhausts memory: confirm the bound bundle is 2.15.1 or later.
  7. Static IP fails: use 192.168.65.0/24, or 192.168.64.0/24 with NAT peers off.

Frequently asked questions

Does vphone-cli jailbreak my physical iPhone?

No. It creates patched research guests on an Apple Silicon Mac.

Is Launchpad 2.15.2 notarized?

No. The official 2.15.2 asset is not notarized. Notarized Launchpad 2.15.0 remains compatible with bundle 2.15.2.

Can Launchpad 2.15 use a 2.14 bundle?

No. It requires a 2.15-series bundle.

Will upgrading erase existing VMs?

Rebinding does not inherently erase them, but snapshot, clone or export first. New 2.15 templates are separate.
