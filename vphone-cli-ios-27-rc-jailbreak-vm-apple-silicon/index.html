vphone-cli 2.13.4 Adds Guest Scripting and Fixes Debug Session

vphone-cli’s 2.13 series now exposes an isolated JavaScriptCore scripting runtime and interactive guest terminal for research VMs. Version 2.13.4 corrects the resource-layout error that made the new Debug Session window trap before appearing.

Latest verified release: Lakr Aream published vphone-cli 2.13.4 on October 25, 2026 at 17:33 UTC. It supersedes 2.13.3, whose new Debug Session interface could fail before its window appeared.

What vphone-cli 2.13.4 fixes

The Debug Session terminal uses GhosttyKit_GhosttyTerminal.bundle. In 2.13.3 that resource was staged beside vphone-vm in Contents/MacOS, while Swift’s Bundle.module looked first in VPhone.bundle/Contents/Resources. Opening the session therefore trapped before the window appeared.

Version 2.13.4 moves the terminal resource into Contents/Resources and updates bundle validation. The resource contains no executable code and is sealed as ordinary resources rather than carrying its own signature. The release also changes the vague Session label to Debug Session; terminals opened on a program retain the Terminal title and show the program underneath.

The developer verified a local Debug build, the new resource layout and strict code-signing validation. The release explicitly says the Debug Session window was not opened on a running guest, so this article does not claim an end-to-end VM test.

Why the 2.13.3 scripting session matters

The preceding 2.13.3 release is the substantial feature update. Its vphoned daemon adds script.eval, which runs JavaScriptCore code in a separate process spawned by the daemon. The child inherits the daemon’s signature and entitlements, while a crash or runaway loop is isolated to that session.

  • Structured result: a script returns ok, result, output and crashed; a thrown error is an answer rather than a failed transport.
  • Timeout: the default is 30 seconds, with an optional per-call limit.
  • Objective-C bridge: an NSInvocation bridge can call methods the runtime describes, and an Objective-C exception becomes a JavaScript error.
  • Helpers: fs, proc, api, console, print and sleep cover files, one program and output.
  • Limits: each guest allows up to eight interactive sessions and sixteen scripts at once.

watchOS does not ship JavaScriptCore, so the daemons advertise script_js only where the runtime exists. The shell capability remains available across the supported guest families.

The guest shell is a WebSocket pseudo-terminal

GET /v1/shell now upgrades to a WebSocket carrying a pseudo-terminal for vphoned’s JavaScript REPL or a bootstrap program. Each session leads its own process group, so programs started by that terminal stop with the session.

On the Mac, Diagnostics → Debug Session (Option-Command-T) uses libghostty’s in-memory backend and the VM process’s VSOCK connection. It does not require --api-listen or an API token. The documented {"t":"shell"} request on vphone.sock reaches the same guest terminal.

The 2.13.3 release reports 149 runtime, bridge, process-mode and pseudo-terminal checks on macOS and the same set in iOS Simulator. Its terminal UI and script.eval were not exercised on a running research guest in that build; 2.13.4 fixes a concrete launch blocker but retains the live-guest testing caveat.

Upgrade path and compatibility boundaries

The official instructions say to install VPhone.bundle 2.13.4 from Launchpad’s Core Bundle page. Existing machines keep their current bundle binding until the user changes it, and a running guest keeps its older daemon until it boots from updated resources.

Launchpad has no functional source change after 2.13.0. Launchpad 2.13.x and Core Bundle 2.13.x remain interchangeable. The 2.13.4 Launchpad ZIP is a CI build and is not notarized, while the notarized Launchpad 2.13.0 continues to work with Core Bundle 2.13.4.

  1. Use the official 2.13.4 release page.
  2. Keep notarized Launchpad 2.13.0 unless a later CI build is specifically needed.
  3. Install Core Bundle 2.13.4 from Launchpad.
  4. Preserve recoverable VM data before changing a machine’s bundle binding.
  5. Boot from the new guest resources before expecting the 2.13.3 scripting daemon.

This is research virtualization, not an iPhone jailbreak release

vphone-cli runs virtual Apple guests on a physical Apple Silicon Mac. Its custom-firmware patches, JavaScript runtime, shell and debugging bridge operate inside those research VMs. Version 2.13.4 does not add an exploit or jailbreak path for a retail iPhone, iPad, Apple Watch, Apple TV or HomePod.

Readers looking for physical-device support should use the Dopamine versus palera1n comparison and check the exact chip and firmware.

Frequently asked questions

What is new in vphone-cli 2.13.4?

It fixes the resource location that caused Debug Session to trap before opening and renames the menu and window from Session to Debug Session.

Can scripts control a running guest?

Version 2.13.3 adds isolated JavaScriptCore execution, an Objective-C bridge and a guest pseudo-terminal. The developer tested the runtime on macOS and iOS Simulator, but did not exercise the terminal UI or evaluator on a running research guest in that build.

Does scripting work on watchOS guests?

No. watchOS does not ship JavaScriptCore, so script_js is advertised only where available. The shell remains supported.

Does vphone-cli 2.13.4 jailbreak a physical iPhone?

No. It is an Apple Silicon Mac virtualization and research platform.
