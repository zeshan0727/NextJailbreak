How to Set Up vphone-cli 2.13.8 on an Apple Silicon Mac

Use the official 2.13 series to create an iPhone research guest without confusing virtual-device support with a jailbreak for physical hardware. This walkthrough covers the host policy, correct downloads, firmware pairing, creation pipeline and recovery checks.

By Zeeshan Barvi · Originally published September 15, 2026 · Updated October 29, 2026

Current version: vphone 2.13.8, released October 26, 2026 at 18:57 UTC. The official Core Bundle ZIP has SHA-256 d79b608886c78246446d8480210ca3f043f4d25d5c6360a029718c84a7395c98.
This is not a physical-device jailbreak. vphone-cli patches and boots research guests on a Mac. It does not add jailbreak support to an iPhone or iPad you own, and a successfully virtualized firmware does not prove that firmware is jailbreakable on retail hardware.

Requirements before you start

  • A physical Apple Silicon Mac running macOS 15 or later. The official host guide says PV=3 guests do not run inside a nested macOS VM.
  • Administrative access and a recovery plan. vphone’s private virtualization entitlement requires changing host security policy. Back up the Mac and understand how to restore its previous SIP and boot-argument state.
  • Enough storage and memory. A new VM defaults to a 64 GB virtual disk, 8 CPU cores and 8192 MB of memory. Prepared firmware and caches consume additional space.
  • Two compatible firmware inputs: an iPhone restore IPSW and a PCC/cloudOS IPSW listed as a verified or supported pairing by the project.
  • Network access during creation for Apple restore tickets and any firmware downloads.

1. Download the correct 2.13 files

The project recommends a notarized Launchpad when one is available. For the 2.13 series, the downloads table lists Launchpad 2.13.0 as the notarized app. Launchpad 2.13.x works with any 2.13.x VPhone.bundle, so install the newest Core Bundle—2.13.8—inside that app.

The separate vphone-launchpad-2.13.8.zip attached to the 2.13.8 release is not notarized; macOS blocks it on first launch. The developer says the notarized 2.13.0 Launchpad remains compatible with the 2.13.8 bundle. CLI users can download VPhone-2.13.8.zip directly from the official release.

Do not download repackaged bundles or firmware from an unofficial mirror. A matching digest proves file identity, not that changing the Mac’s security policy is risk-free.

2. Prepare the Mac’s host policy

Both supported policy paths require csrutil allow-research-guests enable from macOS Recovery. The official host guide then offers two choices:

  • More permissive: disable SIP and AMFI using the documented Recovery and boot-argument commands.
  • More restrictive: keep SIP enabled with debugging restrictions relaxed, then use the bundled vphone-escalator helper to allowlist the current signed vphone-vm.

Prefer the more restrictive route when it works for your setup. Do not paste a replacement nvram boot-args value without first recording existing boot arguments; replacing that variable can remove unrelated settings. The allowlist is tied to the signed build’s cdhash, so the official guide says to repeat the allow command after every rebuild or signature change.

After installing the official bundle, run:

vphone-cli host preflight

If AMFI refuses the entitled companion, preflight prints the exact helper command for that installed bundle. Use that path rather than copying a command that points at someone else’s build directory.

3. Select a verified firmware pair

Start with the project’s live catalogue:

vphone-cli fw catalog

The simple path in the official guide uses an iPhone17,3 restore IPSW with a compatible PCC/cloudOS IPSW. The project’s compatibility table records combinations that actually reached the guest and answered a vphoned ping; it explicitly warns that other pairings may be untested.

Do not infer compatibility from matching version numbers alone. Recent cloudOS releases may lack the vphone600 components used by the older direct path, and some combinations require a research-board kernelcache recipe or a different macOS linker layout. If the catalogue refuses a pairing, choose a listed combination rather than forcing the restore.

4. Create the virtual iPhone

With the two firmware files stored locally, the official one-command flow is:

vphone-cli host preflight
vphone-cli vm create myphone \
  --iphone-source /path/to/iPhone_Restore.ipsw \
  --cloudos-source /path/to/cloudOS.ipsw

The pipeline performs preparation, firmware patching, an online DFU restore, host-mounted custom-firmware installation and a first GUI boot. Root privileges are required for the CFW installation stage; inspect the executable path and follow the official prompt rather than running unrelated scripts with sudo.

By default, current versions build a reusable template and clone the named VM from it. A later VM with the same device, firmware, preset and disk settings can clone that template instead of restoring again. Omit --keep-artifacts unless you deliberately need the large prepared restore tree.

5. Start the VM after creation

A successful creation ends after vphoned answers during the verification boot, then the verification VM stops. That is expected. Start the guest explicitly:

vphone-cli vm launch myphone

Stop it from another Terminal window with:

vphone-cli vm stop myphone

Closing the window, quitting the app or interrupting the launch command first asks the guest to shut down. The VM window provides Home and power keys, app installation and file browsing.

What the new guest does not include

The standard creation workflow leaves the package environment empty. It does not install Sileo, apt, TrollStore, an SSH server or a VNC server. Treat separate package-environment setup as a later task after the base guest boots reliably.

For broader context on physical-device availability, use the site’s iOS 27.2 RC jailbreak status update. For a conventional virtual-machine alternative that does not use vphone’s research-guest pipeline, compare the UTM 5 guide.

Troubleshooting checklist

  1. vphone-vm is killed before a window opens: rerun vphone-cli host preflight. If the bundle was rebuilt or re-signed, its cdhash changed and must be allowlisted again.
  2. “Virtualization is not available on this hardware”: move to a physical Apple Silicon Mac. Nested macOS virtualization is unsupported.
  3. Creation says the ping succeeded but no VM is running: that is normal; run vphone-cli vm launch <name>.
  4. Stuck at “Press home to continue”: use the VM window’s Keys → Home action.
  5. Restore fails: confirm Apple ticket access, compare both IPSWs with the current compatibility table and retry with a new VM name plus -v for detail.
  6. First boot cannot reach vphoned: allow the full 300-second first-boot window. A new guest uses a GUI boot because the daemon may not start during an initial headless boot.
  7. Disk remains open after stopping: vm stop only signals the VM’s own processes. Spotlight, a backup tool or another process holding the disk is reported but not terminated.

Frequently asked questions

Does vphone-cli jailbreak my physical iPhone?

No. It creates patched research guests on a Mac. Nothing in this workflow changes the jailbreak status of a retail iPhone.

Can I use an Intel Mac?

No. The official host requirement is a physical Apple Silicon Mac running macOS 15 or later.

Why use Launchpad 2.13.0 with bundle 2.13.8?

Launchpad 2.13.0 is the notarized release for the 2.13 series. The project documents that 2.13.x Launchpad versions work with 2.13.x Core Bundles and recommends the newest bundle within the series.

Does the VM start automatically after creation?

No. The verification boot stops after a successful vphoned ping. Launch the named VM separately.
