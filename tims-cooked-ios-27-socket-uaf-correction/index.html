Tims‑Cooked iOS 27 Probe Finds ANE Reachability, No decmpfs Readback

A November 25 signed-app test on iPhone18,1 / iOS 27.0.1 build 24A446 reached one ANE service without sending a selector, while bounded decmpfs ingress attempts produced no data-bearing readback. It establishes reachability and negative test results—not memory corruption, an exploit or a jailbreak.

By Zeeshan BarviPublished November 21, 2026Updated November 26, 2026
Bottom line: The November 25 device batch proves only that the signed app can complete its userland self-memory control and open one of 16 enumerated ANE services without sending an external-method selector. Its sandbox-local decmpfs variants produced zero data-bearing compressed reads, left UF_COMPRESSED unset and returned EPERM for filesystem-control attempts. Decoder entry, memory corruption, a kernel primitive, an exploit and a jailbreak all remain unproven.

What the November 25 device probe actually found

The official November 25 source commit documents a bounded signed-app batch on device identifier iPhone18,1 running iOS 27.0.1 build 24A446. The project published no new app binary with this checkpoint. It deliberately avoided broad selector sweeps, malformed GPU or AVE requests, IOSurface method calls, and socket or allocator races.

ModeObserved resultWhat it does not prove

--decmpfsThe plain-file baseline returned 4096 bytes, but tested compressed-data reads returned zero; UF_COMPRESSED stayed unset and filesystem-control variants returned EPERM.No decompressed output was observed, and the source does not claim the decoder was entered or that every decmpfs path is safe.

Device, firmware and jailbreak limits

This result applies only to the documented iPhone18,1 test device on iOS 27.0.1 build 24A446. It is not evidence that the same services are reachable on every iPhone or iOS 27 build. The project’s iPhone 13 Pro secondary device was unavailable, and the higher-risk candidates were not run because they lacked safe ingress, an independent oracle, or the project’s secondary-device no-brick gates.

Crash-report counts stayed at 307 across each fresh mode. A later snapshot added a SpringBoard icon-placeholder fault and an NRD staged-tvOS DYLD abort, but the project does not attribute either event to the probe: the SpringBoard PID and boot session were unchanged, no process death or reboot was established, and a later read-only check found no further reports. Readers should not describe this batch as a crash, respring, exploit or jailbreak.

How to evaluate the next claim

  • For ANE: require a documented external-method call and a measurable security-relevant effect; opening a service alone is insufficient.
  • For decmpfs: require proof that controlled data reached the decoder plus a reproducible oracle such as non-zero decompressed output, a clearly attributable crash, or a memory-safety report.
  • For jailbreak availability: require a released tool and an explicit device/firmware matrix. A probe running on iOS 27.0.1 does not mean iOS 27.0.1 is jailbreakable.

The full measurements and caveats are in the project’s device-probe batch note. For the wider firmware picture, use Next Jailbreak’s current iOS 27.2 jailbreak status and device/build compatibility guide rather than inferring support from research-harness execution.

Previous checkpoint: November 24 IOSurface parser audit

The latest official Tims-Cooked checkpoint, research-2026-11-24-b, was published on November 24, 2026 at 05:03 UTC. Its source commit is 823f998. The review targets iPhone14,2, iOS 27.0 build 24A5390f, with kernelcache SHA-256 6719422222a3b68120f663b2113272b5bcf48d648afe892bbce23b8460ba47dd. It is exact-build static analysis: no device method or selector was called.

The new note expands the earlier selector-0 direct-factory negative to the explicit callback paths of the 0xd4 binary parser. It reviews the parser, factory, forwarding wrapper and parent-stack handling, rather than assuming that a nonzero callback argument proves the callback can construct the required object graph.

  • The direct factory passes x2=x3=w4=0 to the parser. The alternate forwarding wrapper preserves caller arguments, but the caller census does not establish that an IOSurface call reaches it with callback mode enabled.
  • The parser saves x2 as the indirect callback function and x3 as callback context. Its current-parent slot, parent-stack depth and stack base are initialized to zero.
  • The only indexed parent-stack store writes x20, which is either zero or the already-existing current parent. Parent classification and non-null class-parent stores occur only after the parser scans an existing non-null parent-stack entry. The callback return is not the value written into that slot.
  • A store initially mistaken for a parent-stack write is actually an object-table insertion: its base is the separate object-table pointer at [sp+0x70] and its index is the object count.

The whole-cache caller census covered 255 executable file-backed segments, 43,149,776 bytes across 252 fileset members. It found two direct branches to the parser, three to the forwarding wrapper, eight to the factory, 19 on-disk format-8 fixup cells resolving to the factory, and 43 calls to 19 importing loader stubs. All seven IOSurface calls to the relevant import stub set x2=0. Seven other importer calls have stack-derived x2 with unresolved w4 provenance; that is not proof that callback execution occurs. The decoded chained-fixup values are on-disk evidence, not proof of live pointer installation or runtime calls.

Bounded conclusion: In the exact binary parser’s explicit direct and callback parent-stack paths, serialized input cannot seed the first non-null collection parent. The nested object graph required by the reviewed c27200 property path therefore cannot be supplied through that parser mechanism. This supersedes the November 24-a note’s narrower direct-factory scope; it is not a whole-parser memory-safety proof and does not settle the separate text parser.

What this means for iOS 27 users

This finding is tied to one static target: iPhone14,2 on iOS 27.0 build 24A5390f. It is not a compatibility claim for iOS 27.0.1, iOS 27.2, beta builds or other devices. The project’s current README says no kernel read/write primitive, kernel code execution, PAC/SPTM bypass or working jailbreak has been demonstrated.

The release reuses the existing TimsCooked-v0.6.ipa unchanged; it is not a new carrier build. The release records a neutral bundle identifier, no embedded provisioning profile, an ad-hoc signature and no entitlements. It requires re-signing and provisioning before installation. Do not install it expecting a jailbreak, Sileo, tweak injection or persistent root access, and do not treat the research target build as a supported jailbreak firmware.

Previous checkpoint: November 23 IOSurfacePlaneInfo class gate

The project’s November 23 commit f0a0a2e, recorded at 20:44:20 UTC, adds an exact-build static-analysis note for iPhone14,2, iOS 27.0 build 24A5390f. The analysed kernelcache has SHA-256 6719422222a3b68120f663b2113272b5bcf48d648afe892bbce23b8460ba47dd. The scope is kernelcache disassembly and on-disk chained-fixup analysis only: no device method, selector, build or install was run for this update.

The earlier trace found that c27200 calls the object returned for IOSurfacePlaneInfo through vtable slot +0x90. The call site has no direct type test, which left open whether a wrong object type could reach that call. The new note follows the property lookup back through c2c2a4 and helper c54a3c: the helper compares the returned object’s class with a requested metaclass and walks the superclass chain before returning the object.

  • The requested metaclass resolves to OSArray. Its exact-build constructor is at 0xfffffff00a87c058.
  • The class-check helper resolved through the authenticated on-disk fixup at 0xfffffff00804b648 to 0xfffffff00a877130; it follows the superclass link at offset +0x10.
  • The exact-build OSNumber constructor at 0xfffffff00a8acc54 names OSNumber and gives it OSObject as its superclass, not OSArray.

Therefore, a plain OSNumber cannot satisfy the lookup’s OSArray-or-subclass gate and cannot reach the +0x90 call through this property path. This closes that specific wrong-type hypothesis. It does not identify the exact +0x90 method implementation or the concrete subclass actually returned by the helper.

QuestionCurrent evidence
Can a plain OSNumber pass this property lookup?No. The lookup requires OSArray or a subclass.
Is the exact +0x90 implementation known?No. The new note does not identify that method or the concrete returned subclass.
Is the allocation count already bounded?Not in the traced path. The visible n > 3 rejection follows allocation requests of 24*n and 32*n.
Is there a demonstrated input-to-allocation chain?No. The unchecked selector-0 text numeric token has not been connected to the property, an accepted array element or the count.
Is there an exploit or jailbreak?No. The work remains static analysis; reachability and memory-safety impact are unproven.

The ordering of the allocation requests remains worth understanding, but it is not enough to claim an integer overflow or memory corruption. The source has not established an earlier count bound, yet it also has not shown that an attacker-controlled value can reach n. The parser’s unchecked 64-bit accumulator is a separate observation until a concrete dataflow connects it to the accepted OSArray contents or allocation operands.

What would have to be proven next

A stronger result would need to identify the concrete object returned by the property helper and its +0x90 implementation; establish that the relevant IOSurface client and selector are reachable from an ordinary app on the stated build; trace the count back to an input that can actually be controlled; and show that validation cannot prevent an unsafe allocation or access. Only then would a reproducible memory-safety impact and a controlled kernel primitive be meaningful next steps. None is established by this static update.

Earlier November 22 notification-dispatch mapping remains static-only

The November 22 source update, commit 4d47ee1, follows an exact-build static review of the IOSurfaceRoot service on target product iPhone14,2, iOS 27.0 build 24A5390f, with build 24B119 as the comparison. No IOSurface app-open test, selector call, device method test or install was performed for this update.

The analysis links the service’s new-client hook to IOSurfaceRootUserClient, then maps the external-method wrapper to a generic dispatcher and per-client mode tables. The dispatcher uses the incoming selector as a bounded table index. One client-mode branch maps notification registration and per-key removal to handlers; the alternate branch maps those entries to stubs. The mode byte is populated by an entitlement-related initializer check, but the policy meaning of that check is not established.

In comparison build 24B119, client teardown sets a marker while holding the list lock, and notification registration checks that marker under the same lock. That is consistent with preventing a registration from inserting a node after teardown has unlinked it. However, the per-key removal handler does not set the teardown marker, so this comparison does not prove that every re-registration sequence is blocked.

The note also records an analysis limitation: authenticated table pointers were mapped using their low-32 file-offset values into executable ranges, while chained-fixup metadata was not independently decoded. Treat this as a dispatch-path map, not a reproduced race or memory-safety finding. No device method was invoked.

What would have to happen next

The project’s own next checks are still gates, not completed work: trace the userland/MIG open path and service-open policy on the target build; resolve the client-construction and entitlement-related gates; then use a signed, isolated open-only test before attempting any selector or race work. Callback lifetime and client teardown ordering would still need runtime evidence. The project explicitly requires a fresh data-preserving backup before device experiments.

The earlier socket-UAF lead remains withdrawn

The Tims‑Cooked repository previously recorded 20 peer-delivery events in a precision socket test and 109/4 TCP-to-UDP deliveries across two devices. Its November 20, 2026 source review now says those numbers cannot be treated as UAF hit counts.

The reason is specific: the sender incremented its entered counter immediately before calling sendmsg. The test then closed the target descriptor and created reclaimer sockets without reserving that descriptor number. If the syscall resolved after the close, a newly created socket could receive the same numeric file descriptor. Normal descriptor reuse could therefore produce the observed peer bytes or UDP datagram without any stale kernel pointer.

The project also corrected the meaning of doneAtClose. It counted calls whose returns were recorded before the snapshot; it did not prove how many operations were still in flight or when the kernel acquired a file reference.

What a valid rerun needs to change

The erratum describes a concrete next gate. The harness must atomically replace the target descriptor with a pre-opened placeholder using dup2, keep that placeholder open until every sender finishes, and log all target and reclaimer descriptor values. That prevents reclaimer allocations from inheriting the old number.

The ordinary fd-reuse case should be run separately as a control, with distinct target and reclaimer peers. Even then, a delivery event alone would not be enough: the research needs an independent way to prove which kernel object backed the descriptor and whether any memory-safety effect occurred.

Why the evidence boundary matters

Kernel-service class names, method tables and lock checks are useful reverse-engineering landmarks, but they do not show that an ordinary sandboxed app can open the service, reach a selector or control the relevant client mode. A static path map is not a memory-corruption primitive.

The socket correction and the IOSurface follow-up illustrate the same standard: a credible jailbreak claim needs a reachable trigger, a demonstrated memory-safety effect, a controlled kernel primitive and a complete supported-device chain. None of those downstream results is established by this update.

Practical advice for readers

  • Do not install the TimsCooked v0.6 IPA expecting a jailbreak, Sileo, tweak injection or persistent root access.
  • Do not treat the old socket-delivery counters or the new IOSurface dispatch map as proof of an exploitable kernel bug.
  • Look for a signed, isolated service-open test, a verified ordinary-app client mode and runtime evidence about callback and client-free ordering.
  • Require a separate public release with exact device/build support before calling any research project an installable jailbreak.
