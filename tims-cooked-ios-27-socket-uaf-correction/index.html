Tims‑Cooked Retracts iOS 27 Socket-UAF Claim: What the Evidence Now Shows

The project’s own source review found that its earlier “stale write” counters did not rule out ordinary descriptor reuse. That changes what users should—and should not—conclude about the research.

By Zeeshan BarviNovember 21, 2026
Bottom line: Tims‑Cooked has not demonstrated an iOS 27 socket use-after-free, kernel read/write primitive, kernel code execution or jailbreak. The November 20 correction says the historical socket events are inconclusive until a descriptor-safe control is run.

What the project corrected

The Tims‑Cooked repository previously recorded 20 peer-delivery events in a precision socket test and 109/4 TCP-to-UDP deliveries across two devices. Its November 20, 2026 source review now says those numbers cannot be treated as UAF hit counts.

The reason is specific: the sender incremented its entered counter immediately before calling sendmsg. The test then closed the target descriptor and created reclaimer sockets without reserving that descriptor number. If the syscall resolved after the close, a newly created socket could receive the same numeric file descriptor. Normal descriptor reuse could therefore produce the observed peer bytes or UDP datagram without any stale kernel pointer.

The project also corrected the meaning of doneAtClose. It counted calls whose returns were recorded before the snapshot; it did not prove how many operations were still in flight or when the kernel acquired a file reference.

What a valid rerun needs to change

The erratum describes a concrete next gate. The harness must atomically replace the target descriptor with a pre-opened placeholder using dup2, keep that placeholder open until every sender finishes, and log all target and reclaimer descriptor values. That prevents reclaimer allocations from inheriting the old number.

The ordinary fd-reuse case should be run separately as a control, with distinct target and reclaimer peers. Even then, a delivery event alone would not be enough: the research needs an independent way to prove which kernel object backed the descriptor and whether any memory-safety effect occurred.

Current iOS 27 scope and jailbreak status

The repository describes Tims Cooked as an exploratory harness for arm64e devices on iOS 27.0 and 27.0.1. Its README currently states that no kernel read/write primitive, kernel code execution, PAC/SPTM bypass or working jailbreak has been demonstrated.

The project’s November 20 checkpoint was static-only. It compared AppleJPEGDriver code between iOS 27.0.1 build 24A446 and iOS 27.2 build 24B119, but the release explicitly says that work produced no demonstrated vulnerability or jailbreak. The attached v0.6 IPA is unchanged, has SHA-256 dd7a4680155fd738d5b279bf0da3e8debf385a0cf44d8636a0c35a3e1039ce50, and is a research harness—not an end-user jailbreak.

No device support should be inferred from those firmware labels. If you need the practical availability picture, use the iOS 27 jailbreak status hub; for terminology, see the jailbreak compatibility checklist.

Why this correction matters

Race-test output can look persuasive while still measuring an ordinary operating-system behavior. Closing a descriptor releases its number for reuse, while an already-entered syscall may also retain a file reference. A trustworthy exploit claim has to distinguish both cases from a stale kernel-object reference.

The correction is therefore useful progress even though it removes a positive-looking result. It prevents a research observation from being repeated as “iOS 27 jailbreak achieved,” narrows the next experiment, and preserves a clear boundary between candidate investigation and a usable exploit chain.

Practical advice for readers

  • Do not install the TimsCooked v0.6 IPA expecting a jailbreak, Sileo, tweak injection or persistent root access.
  • Do not treat the historical event counts as proof that CVE-2026-112514 works on iOS 27.0.1.
  • Watch for a future fd-pinned rerun and object-identity evidence, not just another delivery counter.
  • Require a separate public release with exact device/build support before calling any research project an installable jailbreak.
