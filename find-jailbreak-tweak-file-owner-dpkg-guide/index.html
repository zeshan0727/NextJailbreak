How to Find Which Jailbreak Tweak Installed a File with dpkg

An unfamiliar dylib, preference bundle or helper binary is not a reason to start deleting files. Query the active dpkg database, identify the owning package, verify its installed state, then make any removal through Sileo or Zebra.

By Zeeshan Barvi · Published October 18, 2026 · Verified against the official dpkg 1.23.11 manual dated September 9, 2026

Safety rule: use these commands only to read package records. Do not run rm, edit dpkg’s status files, or force-remove a package because one pathname looks suspicious.

Quick answer

Open a terminal inside the active jailbreak environment and ask dpkg which installed package owns the exact file:

dpkg-query -S '/var/jb/Library/TweakInject/Example.dylib'

A normal match looks like this:

com.example.tweak: /var/jb/Library/TweakInject/Example.dylib

The text before the colon is the package identifier. Copy that identifier into the commands below, then find the same package under Sileo → Packages → Installed before deciding whether to keep or uninstall it.

Before you query a path

  1. Use the active jailbreak. A rebooted semi-untethered device may be outside its normal jailbreak environment.
  2. Copy the exact absolute path. Do not convert a rootless path to a rootful path or guess where RootHide placed it.
  3. Stay unprivileged. The official dpkg-query manual says query operations should never require root. Do not add sudo merely to search the database.
  4. Record the result. Save the package ID, version, architecture and status before changing anything.

Step 1: find the package that owns the file

Replace the example with the exact path you found:

dpkg-query -S '/exact/path/to/the/file'

-S (or --search) searches the installed-file records. Quote the path so the shell does not expand wildcard characters or split spaces. A result can name more than one package when diversions are involved; do not discard that detail.

If you know only the filename, try a quoted wildcard after the exact-path lookup:

dpkg-query -S '*Example.dylib'

The dpkg manual says its wildcard search can match slashes, so this broader query may return several paths. Treat the full returned path—not just a familiar filename—as the evidence.

Step 2: verify package, version, architecture and state

Replace com.example.tweak with the returned identifier:

dpkg-query -W -f='${binary:Package}\t${Version}\t${Architecture}\t${db:Status-Status}\n' com.example.tweak
FieldWhy it matters
binary:PackageConfirms the identifier, including an architecture qualifier when dpkg needs one.
VersionLets you compare the installed build with the developer’s official listing.
ArchitectureHelps confirm that the package belongs to the active rootful, rootless or other bootstrap environment.
db:Status-StatusShows whether dpkg considers it installed, unpacked, half-configured or in another state.

An installed result means dpkg considers the package correctly unpacked and configured. A partial state is a package-database problem, not permission to delete its files manually; use the dpkg interruption repair guide.

Step 3: list every tracked file in that package

dpkg-query -L com.example.tweak

-L lists files dpkg recorded for the package and also reports diversions. This is useful when a tweak has a dylib, plist, Settings bundle and helper binary under different directories.

The official manual documents an important limit: -L and -S do not list extra files created by maintainer scripts, and they do not list alternatives. A package can also create preferences or caches later while it runs. Therefore, “no path found” does not prove that a file is safe to delete or that no package created it.

How to handle “no path found”

  1. Run the exact-path query again with the path in single quotes.
  2. If the path is a symlink, query both the link path and its resolved target; record which one matches.
  3. Search the basename with a quoted wildcard and compare complete paths.
  4. Check whether the file is user data, a preference, cache or runtime-generated output rather than a packaged file.
  5. Confirm that you are querying the dpkg database for the active jailbreak environment, not a different rootful, rootless or RootHide setup.
  6. If ownership remains unclear, stop and ask the package developer or jailbreak project before deleting anything.

Remove the package, not a single tracked file

When you decide the identified tweak should be removed, open its exact package ID in Sileo or Zebra. Review the full queued transaction and uninstall through the package manager. This lets dpkg run the package’s removal scripts, update its database and process triggers.

Cancel if the queue proposes removing Sileo, Zebra, APT, dpkg, the bootstrap, the tweak-hooking framework, or unrelated packages you did not intend to remove. Follow the safe Sileo uninstall guide for the queue review and completion action.

What these commands do not prove

  • A package owning a file does not prove that the package caused a crash.
  • A familiar developer or package name does not prove the installed build came from an official repository.
  • A tweak’s stated iOS range does not prove a jailbreak exists for every device on that firmware.
  • A rootless architecture label does not make an ordinary rootless package interchangeable with a RootHide-specific build.
  • A clean dpkg-query result does not assess source trust, code quality or runtime behavior.

Command order

1. Exact path: dpkg-query -S

2. Package facts: dpkg-query -W

3. Tracked files: dpkg-query -L

4. Remove through Sileo or Zebra

Never: delete dpkg records or tracked files by hand.
