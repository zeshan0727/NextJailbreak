How to Inspect a Jailbreak .deb Before Installing It

A package manager can resolve dependencies and install files, but its confirmation screen does not tell you everything inside an unfamiliar package. Before you queue a downloaded .deb, use dpkg-deb to read its identity, relationships, maintainer scripts and payload without installing it.

By Zeeshan Barvi · Published October 19, 2026 · Verified against the official dpkg 1.23.11 manual dated September 9, 2026

Safety boundary: inspect untrusted archives as a normal user, not as root. These commands do not install the package or execute its scripts. Read extracted scripts as text—never run them just to see what they do.

Quick inspection sequence

On Linux, WSL, macOS with the dpkg tools installed, or a terminal inside an APT/dpkg-based jailbreak environment, replace package.deb with the downloaded filename:

dpkg-deb --info package.deb
dpkg-deb --field package.deb Package Version Architecture Depends Pre-Depends Conflicts Replaces
dpkg-deb --contents package.deb
mkdir deb-control
dpkg-deb --control package.deb deb-control

The first two commands read the control metadata, the third lists the data payload, and the last copies the control files—including any maintainer scripts—into a directory you can review. None is an installation command.

Step 1: establish where the file came from

Inspection starts before the terminal. Prefer the developer’s official repository, release page or package source. A reuploaded package can retain the same filename, icon, identifier and version while containing different binaries or scripts. If the developer publishes a SHA-256 checksum, compare it with your download before opening the archive.

A Debian archive does not contain a built-in publisher authentication mechanism. The official dpkg-deb manual distinguishes archive handling from higher-level repository authentication: APT can authenticate packages downloaded from a configured repository, but a loose .deb does not authenticate itself. A checksum is useful only when you obtained the expected value through a trusted channel.

Step 2: read the control metadata

Start with the full information view:

dpkg-deb --info package.deb

Then request the fields that most directly affect a jailbreak installation:

dpkg-deb --field package.deb \
  Package Version Architecture \
  Depends Pre-Depends Conflicts Replaces
FieldWhat to verify
PackageThe identifier should match the developer’s listing. An imitation can use a convincing display name.
VersionConfirm that it is the release you intended to download, not an older or unexpectedly modified build.
ArchitectureMatch the package format to the target jailbreak environment; do not infer support from the filename alone.
Depends / Pre-DependsIdentify libraries, firmware constraints and frameworks the package requires.
Conflicts / ReplacesUnderstand which installed packages or files it may displace before Sileo queues a transaction.
MaintainerCompare the declared maintainer with the official source, while remembering that archive metadata is editable and is not proof of identity.

Step 3: match the package to the jailbreak environment

Theos documents iphoneos-arm for traditional rootful packaging and iphoneos-arm64 for conventional rootless packaging. It also documents the rootless package scheme’s /var/jb prefix and notes that current rootless support targets iOS 15 and later. Those values help catch an obvious mismatch, but they do not prove the package supports your exact device, iOS version, bootstrap or tweak-injection framework.

Read the dependency fields as well as the architecture. Theos explains that a package can depend on the firmware meta-package to set a minimum iOS version. A developer may also publish separate builds for conventional rootless and RootHide environments. Do not substitute one merely because both are described as “rootless,” and do not treat a package’s iOS range as proof that a public jailbreak exists for every device on those versions.

If you are unsure which environment is active, stop and use the rootless jailbreak basics guide before installing anything.

Step 4: list every payload path

dpkg-deb --contents package.deb

The output is a tar-style listing with permissions, ownership, size and path for each payload item. Review the complete list, not just filenames that contain the tweak’s name.

  • For a conventional rootless package, expect installed content to be rooted under /var/jb. Theos rootless v2 can relocate the jailbreak root internally, but packages still use the documented rootless layout.
  • Look for launch daemons, command-line helpers, preference bundles and tweak-injection dylibs so you understand the package’s reach.
  • Notice set-user-ID bits, unusual ownership or unexpectedly broad permissions. They are not automatically malicious, but they need a purpose.
  • Question files that overwrite unrelated applications, package-manager components or bootstrap paths.
  • Compare the listing with the feature advertised by the developer. A simple theme and a persistent privileged daemon have very different risk profiles.

A path list is evidence, not a verdict. Legitimate system utilities can require broad access, while a malicious payload can hide inside an ordinary-looking binary.

Step 5: extract and read the control files

Create an empty directory and extract only the control archive:

mkdir deb-control
dpkg-deb --control package.deb deb-control
ls -la deb-control

Theos recognizes the standard maintainer scripts preinst, postinst, prerm and postrm, plus the jailbreak-oriented extrainst_. Package managers run these scripts at defined points during installation, upgrade or removal, with the authority needed to modify the environment. That makes them essential reading.

Open any scripts in a text editor. Check which processes they stop, which directories they create or delete, whether they modify other packages’ files, what commands they invoke and whether they fetch anything from the network. A respring or preference cleanup can be normal; opaque downloads, broad recursive deletion, credential access or unrelated system changes demand a clear explanation from the developer.

Do not execute extracted scripts manually. Their assumptions about package-manager state and arguments may be wrong outside the intended lifecycle, and an untrusted script should never receive authority merely for inspection.

Optional: inspect the raw control archive

If you want a listing before extraction, the official tool can send the control tar archive to standard output:

dpkg-deb --ctrl-tarfile package.deb | tar -tvf -

This reveals the control members and permissions without installing the package. Use dpkg-deb --fsys-tarfile package.deb similarly when you need to pass the data payload to another read-only tar operation.

What counts as a stop signal?

  • The package did not come from the developer’s official channel and no trusted checksum is available.
  • The identifier, version, architecture or declared maintainer does not match the official listing.
  • Dependencies request an unfamiliar repository or an unrelated privileged framework.
  • A conventional rootless package writes outside the expected rootless layout without a documented reason.
  • A maintainer script downloads executable code, deletes broad paths, edits unrelated packages or hides errors.
  • The payload includes privileged helpers or daemons that the advertised feature does not explain.
  • The package conflicts with or replaces core package-manager, bootstrap or injection components unexpectedly.

A stop signal is a reason not to install until the official developer explains it. It is not, by itself, proof of malware.

What this inspection cannot prove

dpkg-deb exposes packaging structure, not runtime intent. It cannot prove what a compiled dylib or executable does, which servers it contacts, whether it collects data, whether embedded code is vulnerable, or whether the binary matches public source code. It also cannot prove that a familiar maintainer name is genuine.

For an open-source package, compare the release checksum and documented build process when available. For a closed-source package, source reputation, repository authentication, change history and the minimum privileges required by the feature matter even more. No single green flag makes an untrusted package safe.

Install only after the preflight checks pass

If the source, checksum, metadata, environment, payload and scripts are all credible, continue with the safe Sileo .deb installation guide. Review the complete transaction before confirming. Sileo may reveal dependency changes that were not obvious from one archive alone.

If the package manager reports unresolved relationships, do not force the installation. Use the Sileo dependency-error guide. After installation, the dpkg file-owner guide can identify which installed package owns a path, but that is a diagnostic step—not a substitute for this pre-install inspection.

Official sources

  • Official Debian dpkg-deb 1.23.11 manual — documents the information, field, contents, control and tar-stream commands; warns against handling untrusted archives as root; and explains that a .deb does not authenticate itself.
  • Debian Policy: binary package control files — defines architecture and package-relationship fields.
  • Official Theos packaging documentation — documents jailbreak architectures, firmware dependencies and maintainer scripts.
  • Official Theos rootless documentation — documents the rootless package scheme, /var/jb layout and rootless v2 behavior.
  • Official Theos logo source — source of the original project artwork embedded above.

Sources checked October 19, 2026. The commands are documented read-only archive operations; this guide does not claim hands-on testing of every package, bootstrap or jailbreak environment.

Pre-install checklist

1. Verify source and checksum

2. Read identity and relationships

3. Match architecture and environment

4. Review every payload path

5. Read scripts; never run them

6. Inspect Sileo’s full queue
