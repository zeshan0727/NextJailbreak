How to Check If an iOS Version Is Still Signed with TSSChecker

TSSChecker asks Apple’s TSS service whether a specific firmware request is currently being signed. It can answer a useful preflight question, but it does not make an unsigned version installable, prove jailbreak compatibility or guarantee that saved blobs can restore later.

By Zeeshan Barvi · Published November 16, 2026 · Updated November 26, 2026 · Verified against TSSChecker Build 450, its merged Cryptex fix, FutureRestore warnings and Apple Support

Quick answer: download TSSChecker only from its official Build 450 release, verify the SHA-256 GitHub publishes for that exact platform asset, identify the device ProductType, then run tsschecker -d PRODUCTTYPE -i VERSION. A read-only status check does not require an ECID. Saving device-specific tickets—and especially iOS 16+ Cryptex data—is a separate workflow with hardware, nonce and restore-component requirements.

What is current—and what is not

The official TSSChecker project published Build 450 on November 17, 2026 at 14:54 in Qatar. The release points to commit 4d9a7875 and says it fixes Cryptex blob saving. Its merged source change is intentionally small: it removes a Rap-name filter so custom Cryptex tag collection is no longer limited to manifest keys that contain both Cryptex and Rap.

The release provides Windows x86_64, macOS arm64 and x86_64, plus Linux builds for aarch64, arm, mips, mipsel, riscv32, riscv64 and x86_64. GitHub publishes a SHA-256 digest for each asset. Next Jailbreak checked the official release metadata, source commit, merged patch and tagged README; we did not execute Build 450, save a personal ticket or perform a restore.

Step 1: identify the exact device and target

TSS requests use Apple’s ProductType, such as iPhone10,3, rather than only a marketing name such as “iPhone X.” Record the exact iPhone or iPad model, current iOS build and target firmware before checking. Our model and iOS build guide explains how to collect those values without exposing a serial number, IMEI or Apple Account.

Build numbers matter when two releases share a visible version label or when you are checking an RC, beta or OTA build. TSSChecker accepts -i VERSION for a firmware version or -Z BUILD for a specific build identifier. Do not round one version to another.

Step 2: download Build 450 and verify it

  1. Open the official TSSChecker Build 450 release.
  2. Choose the asset for the computer’s operating system and CPU. A Windows x86_64 executable is not the macOS arm64 build.
  3. Compare the file’s SHA-256 with GitHub’s published digest before running it. Follow our SHA-256 verification workflow; the same identity principle applies even though this is a desktop executable.
  4. On macOS or Linux, make the file executable only after the hash matches: chmod +x ./tsschecker.

For the official Linux x86_64 Build 450 asset, GitHub publishes:

e993f5c03b7742976ae56eead781973ede76859efac029cedba5302de25e863a

This digest applies only to tsschecker_linux_x86_64 from release 450. Every other platform asset has its own digest on the release page; do not reuse this value for macOS, Windows or another Linux architecture.

Step 3: run a read-only signing check

From Terminal, Command Prompt or PowerShell, use the syntax below and replace both placeholders with real values:

tsschecker -d PRODUCTTYPE -i VERSION

For an exact build rather than a version label:

tsschecker -d PRODUCTTYPE -Z BUILDID

To ask for the latest public firmware known to the tool:

tsschecker -d PRODUCTTYPE -l

A basic status check can use randomized device values because it asks whether Apple is signing that device/firmware combination generally. The official README explicitly distinguishes this from saving reusable tickets, which needs correct device-specific values.

OTA signing is a separate check

Use -o or --ota to query OTA signing instead of the normal restore path:

tsschecker -d PRODUCTTYPE -i VERSION --ota

An OTA ticket can be available when a normal IPSW restore ticket is not. That does not mean Finder, Apple Devices or FutureRestore can perform the downgrade you want. Record which request type produced the result.

What Build 450 fixes for Cryptex requests

The merged Build 450 patch changes how TSSChecker selects custom Cryptex manifest tags. Build 449’s code skipped a manifest entry unless its key contained both Cryptex and Rap. Build 450 removes the second filter, so other Cryptex-named entries can be included in the request.

This is a request-construction fix, not a new jailbreak or universal downgrade method. The tagged README still says iOS 16 Cryptex1 tickets require a jailbroken device and checkm8-class access to save and use, along with the correct Cryptex seed/nonce values. If you only want signing status, stay with the read-only commands above and do not invent placeholder ECID, generator, APNonce or Cryptex values for a ticket you hope to reuse.

Checking status is not the same as saving SHSH blobs

The --save option writes a fetched ticket, but a reusable device ticket must match the actual hardware and nonce conditions. The official help exposes ECID, generator, APNonce, board configuration, baseband serial and Cryptex values because modern restores cannot be reduced to one universal command.

  • ECID is device-specific. A blob saved for another device is not yours.
  • arm64e nonce entanglement matters. The project documentation requires a matching APNonce and generator pair for reusable arm64e tickets.
  • Baseband tickets can matter. Devices with cellular baseband may require the correct baseband serial data for a valid BBTicket.
  • iOS 16 added Cryptex1. Build 450 fixes custom Cryptex tag selection, but the official README still says saving and using Cryptex blobs requires a jailbreak and checkm8-class access; a normal status query does not create those prerequisites.
  • Saving a file is not proof of future usability. Validate the ticket’s identity and keep the generator, APNonce, ProductType, board configuration, ECID, target version and build together.
Privacy: do not post your ECID, serial, IMEI, baseband serial or full ticket publicly. A signing-status question usually needs only the ProductType, firmware/build, request type and sanitized output.

Why a valid blob still may not restore

FutureRestore’s official README describes unsigned restores as conditional: the APTicket must match the ECID, APNonce and board identity, while the target firmware must remain compatible with the SEP and baseband components available for the restore. On newer systems, Cryptex compatibility adds another boundary.

That is why these three statements are different:

  1. Apple is signing the firmware now. A current TSS request succeeds.
  2. I saved a valid device-specific ticket. The ticket matches the device and nonce information.
  3. I can restore or downgrade later. A current tool and compatible SEP, baseband, Cryptex and restore path all exist.

Do not follow an old FutureRestore tutorial solely because GitHub labels v194 “Latest.” The project’s own v194 page says it is deprecated, may bootloop a device and should be replaced with its current nightly builds. Even a nightly does not remove device and firmware compatibility requirements.

Signing status does not prove jailbreak availability

A signed version may have no public jailbreak for your device. Conversely, an unsigned firmware may have a historical jailbreak but no usable restore path. After the signing check, compare the exact model, firmware and build with current project documentation:

Troubleshooting checklist

  1. “Command not found”: run the binary from its directory, include ./ on macOS/Linux and confirm execute permission.
  2. Wrong architecture: download the matching macOS, Windows or Linux CPU asset.
  3. macOS blocks execution: verify the official digest first, then review the exact Gatekeeper warning. Do not disable system-wide protections for an unverified binary.
  4. Device not found: use ProductType, not a retail name; Build 450 includes the device definitions carried forward from Build 449.
  5. Version ambiguity: query the exact build with -Z.
  6. Unexpected OTA result: check whether --ota was used and repeat the normal request without it.
  7. Cached data looks stale: retry with --nocache; keep the raw error if Apple’s service is unreachable.
  8. You intend to restore: stop at the status check until device-specific blobs, nonce data and current SEP/baseband/Cryptex compatibility are independently verified.

Frequently asked questions

Does signed firmware mean my iPhone can jailbreak it?

No. Signing and jailbreak availability are separate checks.

Do SHSH blobs guarantee a future downgrade?

No. The ticket, device nonce conditions and compatible restore components must all align.

Are OTA and normal restore signing the same?

No. Use --ota only for the OTA lane and label the result accordingly.

Should I use FutureRestore v194 because GitHub marks it Latest?

No. Its own release page says to stop using it, warns it may bootloop and directs users to nightlies.
