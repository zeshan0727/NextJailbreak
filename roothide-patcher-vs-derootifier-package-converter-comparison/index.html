RootHide Patcher 2.1.4 vs Derootifier 1.3: Which Package Converter Do You Need?

These tools are often treated as substitutes, but they solve opposite halves of the package-conversion problem. Pick by the DEB you have and the jailbreak environment you already use.

Published November 21, 2026Primary-source comparison
Quick answer: use Derootifier 1.3 for an eligible legacy iphoneos-arm package that must become a conventional rootless iphoneos-arm64 package. Use RootHide Patcher 2.1.4 only when you already have a conventional rootless package and need a RootHide iphoneos-arm64e build. If the developer already supplies your environment’s package, install that original build instead.

What Derootifier changes

The maintained palera1n fork describes Derootifier as a converter for jailbreak DEBs that need conventional rootless support. Its bundled repack-rootless.sh relocates package content under /var/jb, moves MobileSubstrate libraries into /var/jb/usr/lib/TweakInject, changes the package architecture to iphoneos-arm64, rewrites common library paths and adds rootless run paths before signing Mach-O files with Procursus ldid.

The same script explicitly says it performs no further modification. That matters: a package can be repacked successfully and still fail because its code, scripts, dependencies or preference bundle assume a rootful filesystem.

What RootHide Patcher changes

RootHide Patcher starts one step later. Its official package is itself iphoneos-arm64e, and its README says it patches a rootless package for RootHide. The current control file identifies version 2.1.4 and iOS 15 or later; the project’s February 25, 2026 commit is the exact version bump.

Do not feed it a legacy rootful DEB and assume it will perform Derootifier’s conversion first. Follow the dedicated RootHide Patcher guide for package inspection, patch modes and the correct RootHide installation flow.

Why a converted DEB can still fail

  • Hard-coded paths: binaries, preference bundles and scripts may reference locations the converter does not rewrite.
  • Injection framework assumptions: a package may expect Cydia Substrate, Substitute, ElleKit or a specific loader and fail in another environment.
  • Daemons and launch services: launch daemons, entitlement requirements and privileged helpers are not made portable by changing the package architecture.
  • Dependencies: the converted package may still depend on a library that has no build for the target environment.
  • DRM and licensing: conversion does not bypass a license check. Do not convert or redistribute a paid package without the developer’s permission and a valid purchase.
  • Firmware-specific code: a package written for older UIKit or private APIs can remain incompatible even when its filesystem paths are correct.

Use the tweak compatibility checklist before conversion. A package’s iOS range is not evidence that every device on that firmware can be jailbroken.

Safe conversion and recovery checklist

  1. Confirm your exact environment with the rootless, rootful and RootHide guide. Do not choose a converter from the tweak’s marketing description alone.
  2. Prefer an official rootless or RootHide build. Convert only when the developer has not supplied the environment you need and the package license permits it.
  3. Keep the original DEB untouched. Record its filename, package identifier, version and architecture before producing a separate converted copy.
  4. Inspect dependencies and maintainer scripts. A successful conversion message is not a compatibility test.
  5. Install through your normal package manager; see the rootless DEB installation guide. Change one package at a time and respring before adding anything else.
  6. If SpringBoard crashes, boot with tweak injection disabled, remove the converted package and its newly installed dependencies, then respring. The Dopamine crash-loop recovery guide provides the safe sequence.
