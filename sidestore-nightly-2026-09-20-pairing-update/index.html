SideStore 0.7.0 Nightly: September 20 Pairing Changes Explained

SideStore’s build 0.7.0-20260920.1479+0dd743f7 is an experimental nightly snapshot built on September 20, 2026. The update concentrates on pairing architecture rather than presenting a stable SideStore 0.7.0 release. Its changelog lists dual pairing-file support, a pairing file manager, preferred-protocol handling, pairing-flow refinements, prompt and cleanup changes, a session-level delegate adjustment, and the move of hotswap into the experimental area. The source does not claim broader platform compatibility, automatic seamless switching, or guaranteed fixes for every pairing or protocol problem.

\n \n
\n

Key points

  • This is an experimental nightly snapshot, not a stable SideStore 0.7.0 release.
  • The build was produced on September 20, 2026 and is identified as 0.7.0-20260920.1479+0dd743f7.
  • The central functional change is implementation of dual pairing-file support, alongside a new pairing file manager and pairing-flow restructuring.
  • Preferred-protocol handling was revised, including fixes for protocol-mismatch presentation and cases where the loaded pairing was not the preferred one.
  • Hotswap was moved into the experimental category, so the changelog does not support treating it as a mature or universally reliable feature.
  • Readers should preserve their existing pairing information and review the current nightly details before installing, because the maintainers explicitly describe nightly builds as highly experimental.
\n

What this snapshot is—and what it is not

The September 20 snapshot carries the version string 0.7.0-20260920.1479+0dd743f7 and was built at 03:17:25 UTC on September 20, 2026. The associated commit is 0dd743f75afc358b0ba4a002feb5f19474492371. Those identifiers matter because the release page labels the item “Nightly” and “Pre-release,” while the changelog itself describes it as an experimental build for developers and beta testers.

It should therefore not be reported as a final SideStore 0.7.0 release. The “0.7.0” portion is part of the nightly version naming, while the date and commit suffix identify this particular build. The release page also warns that nightly builds can contain bugs and experimental features and should be used at the user’s own risk.

  • Build date: September 20, 2026, at 03:17:25 UTC.
  • Nightly version: 0.7.0-20260920.1479+0dd743f7.
  • Commit: 0dd743f75afc358b0ba4a002feb5f19474492371.
  • Release status: experimental nightly and pre-release, not stable 0.7.0.

Dual pairing files change the pairing model

The most consequential entry in the changelog is “implement dual pairing file support.” Other entries describe a “pairing file manager,” centralization of pairing management, movement of supported pairing types into that manager, and cleanup of the boot manager to reflect a new pairing flow. Taken together, the documented direction is a reworked internal and user-facing organization for handling pairing files.

The wording supports saying that this snapshot can work with two pairing files in the pairing architecture. It does not, by itself, explain every supported pairing type, define how users should choose between files, or promise that two files will be used simultaneously in every workflow. The source also does not claim that dual support expands SideStore’s overall device or operating-system compatibility.

The pairing file manager is important because the changelog says pairing-management responsibilities were centralized there. That suggests the update is intended to give the pairing flow one place to handle pairing-file-related decisions. However, the source does not publish a complete user manual for the manager in the release material, so installation instructions should not be inferred from the code-organization notes alone.

The changelog also mentions renaming pairing-file names to be the same length and moving name handling into a separate row. These are interface and organization refinements, but the source does not describe them as a new security feature or as evidence that older pairing files are automatically migrated in every case.

  • Dual pairing-file support is explicitly listed as implemented.
  • Pairing management was centralized into a pairing file manager.
  • Supported pairing types were moved into that manager.
  • The source does not document automatic migration, universal pairing compatibility, or seamless switching between all pairing files.

Preferred protocols, prompts, and mismatch handling

Several entries concern the relationship between a loaded pairing file and the preferred protocol. The nightly changelog lists fixes for markdown rendering in a protocol-mismatch-versus-preferred state, cleanup and re-prompting when the loaded pairing was not the preferred one, and a fix to stop inadvertently overwriting the preferred protocol.

In practical terms, the wording points to clearer handling of a mismatch: SideStore can recognize that the currently loaded pairing is not the one marked as preferred, clean up relevant state, and prompt again according to the revised flow. The markdown-rendering entry indicates that at least some of the related messaging or presentation was corrected. These are documented changes to handling and presentation, not a promise that every protocol mismatch disappears.

The preferred-protocol fix is especially important because the changelog says the previous behavior could inadvertently overwrite the preferred protocol. The stated change supports a narrower conclusion: this snapshot adjusts that preference-preservation logic. It does not establish that SideStore can automatically select the best protocol in every situation, or that users will never see another pairing prompt.

The source also lists “pairing flow refinements,” “deeplink handling” moved into its own files, and a view/view-model split. Those entries indicate broad restructuring around pairing interactions, but they do not provide a step-by-step workflow or a guarantee that an existing setup will behave identically after updating.

  • Protocol-mismatch presentation received a documented markdown-rendering fix.
  • The nightly includes cleanup and re-prompt behavior when the loaded pairing is not preferred.
  • A separate fix addresses accidental overwriting of the preferred protocol.
  • No source statement promises automatic, seamless protocol switching.

The session-level delegate fix and experimental hotswap

One changelog entry says SideStore should use a session-level delegate instead of a task-level delegate. The associated commit shows this adjustment in the download operation. It adds an active download-task reference and cancellation handling, while the download call no longer creates and passes a delegate for that individual task in the same way as before.

For users, the safest interpretation is that this is an implementation correction in download-task and delegate ownership. It may be relevant to progress reporting or cancellation behavior because the displayed change tracks the active download task and cancels it when the operation is cancelled. The source does not claim a measurable performance improvement, a complete fix for all download failures, or a guaranteed resolution of a particular user-facing bug.

The release notes also say “move hotswap into experimental for now.” That is a status change, not a promise of stable hotswap behavior. The official source does not define the full hotswap workflow, list compatible devices, or state that apps can switch pairing contexts without interruption. Readers should avoid turning the word hotswap into a claim of automatic seamless switching.

  • The delegate change is documented at the download-operation level.
  • The commit adds tracking and cancellation for an active download task.
  • Hotswap was moved into experimental status.
  • The source does not guarantee reliable hotswap, seamless switching, or universal download fixes.

What to verify before installing a nightly

SideStore’s project page describes the application as an untethered, community-driven alternative app store for non-jailbroken iOS devices and lists iOS 14+ among the project requirements. Those are project-level statements, not a nightly-specific compatibility matrix. The September 20 release page does not add a device-by-device or operating-system compatibility statement for this snapshot.

Before changing an existing setup, readers should identify the exact build they are considering and confirm that it is the September 20 snapshot if that is the intended target. They should also preserve access to their current pairing information and avoid assuming that the new dual-file flow will automatically reproduce their existing preferred pairing choice.

Because the maintainers label the build experimental, users should expect that pairing prompts, protocol selection, download behavior, or hotswap may change again in a later nightly. The supplied documentation does not provide a rollback procedure, so a cautious user should review the current official release information and project documentation before proceeding. Use only the project’s official distribution channels; do not rely on unofficial mirrors or modified packages.

The separate alpha 503 issue should not be conflated with this snapshot. The September 20 nightly’s documented scope is pairing, protocol preference, flow cleanup, delegate handling, and experimental hotswap. The official release notes do not say that it is a general solution for every other error condition.

  • Check the full nightly version and commit, not only “0.7.0.”
  • Back up or otherwise preserve existing pairing information before changing the setup.
  • Treat iOS 14+ as the project’s listed requirement, not as proof of additional nightly-specific compatibility.
  • Review current official release notes because rolling nightly references can change.
  • Do not infer a fix for unrelated errors from this pairing-focused changelog.

Frequently asked questions

Is SideStore 0.7.0-20260920.1479+0dd743f7 a stable release?

No. The source labels it an experimental nightly and pre-release build intended for developers and beta testers. The 0.7.0 text is part of the nightly version identifier, not evidence that a stable 0.7.0 release has shipped.

What does dual pairing-file support mean here?

The changelog explicitly says dual pairing-file support was implemented and also describes a pairing file manager. The release material does not fully document the user workflow, automatic migration behavior, or every supported pairing type, so those details should be checked in the current official documentation.

Does the update automatically switch between protocols?

The release notes describe preferred-protocol handling, mismatch presentation fixes, cleanup, re-prompting, and protection against accidentally overwriting the preferred protocol. They do not promise automatic or seamless switching in every situation.

What is the session-level delegate fix?

The associated commit changes download handling from a task-level delegate approach toward a session-level delegate arrangement. It also tracks an active download task and adds cancellation handling. The source does not guarantee that this resolves every download or progress issue.

Should everyone install this nightly?

The maintainers explicitly describe nightly builds as extremely experimental and warn that they can contain bugs and experimental features. Users should verify the exact build, preserve pairing information, review current official instructions, and decide whether experimental pairing changes are appropriate for their setup.
