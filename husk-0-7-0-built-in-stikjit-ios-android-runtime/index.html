Husk 0.7.0 Adds Built-In StikJIT, Wi-Fi for All Games and a Swift UI

Husk 0.7.0 is a major usability update for the Android-on-iPhone project. It adds built-in StikJIT, expands Wi-Fi support across games, rebuilds the interface in Swift, promotes the Translation Layer into the main navigation and adds Beach Buggy Racing 2 support at 60 FPS.

By Zeeshan Barvi · Published October 6, 2026 · Verified against the official Husk 0.7.0 release and merged StikJIT implementation

Latest release: Husk 0.7.0 was published October 6, 2026 and is now the current official release. The downloadable IPA is attached directly to the developer's GitHub release.

What changed in Husk 0.7.0?

The official 0.7.0 changelog lists four headline changes: built-in StikJIT, Wi-Fi support for all games, a fully Swift user-interface revamp, and the Android Translation Layer moved into the four main tabs in place of the old Discover tab.

The same release adds a new tested game: Beach Buggy Racing 2 at 60 FPS. That joins the growing list of Android workloads Husk's developers are actively targeting rather than implying that every APK will automatically work.

Built-in StikJIT is the biggest change

Husk can now handle the JIT debugger role itself through a bundled helper based on StikJIT 1.9.0. The merged implementation says this built-in route is for iOS 26 and newer and communicates over LocalDevVPN. In other words, StikDebug no longer has to be a separate app when the built-in route is configured correctly.

This is especially useful for non-jailbroken devices, where Husk still needs executable memory for its runtime. The helper exists as a separate process because an app cannot synchronously debug itself; it attaches to Husk, prepares the JIT region and then Husk can detach after the executable region is secured.

Need setup steps? Use the Husk 0.7.0 JIT guide for the exact built-in StikJIT, StikDebug and TrollStore workflows, including the iOS 26 versus iOS 27 pairing difference.

Important: iOS 26 and iOS 27 pairing are different

The new built-in JIT does not mean every iOS 26 user can complete pairing entirely on the phone. The merged StikJIT work makes the distinction clear:

  • iOS 26: built-in StikJIT is supported, but you can import a device pairing file made on a computer.
  • iOS 27: Husk can also perform the pairing step on-device. The iPhone pairs with “Husk” from Settings → Privacy & Security → Developer Mode using the code Husk displays.

Husk's setup flow also keeps StikDebug and TrollStore as alternative JIT methods, plus an Automatic mode. Existing StikDebug setups are therefore not removed by 0.7.0.

Wi-Fi support expands to all games

Version 0.6.1 specifically added Wi-Fi support for Unity games. The 0.7.0 release notes broaden that statement to Wi-Fi support for all games. This should make online-capable Android titles and apps more practical inside Husk, although individual games can still have their own server, login, anti-cheat or Google-services requirements.

The interface has been rebuilt in Swift

Husk 0.7.0 also ships a UI revamp that the developer describes as now being fully built with Swift. The Translation Layer is no longer buried as a secondary experimental area: it replaces Discover in the main four-tab navigation, making the APK translation workflow much easier to reach.

That matters because Husk currently combines more than one approach to Android execution. Bringing the Translation Layer into the primary navigation makes the experimental APK path feel like a first-class part of the app rather than a hidden test screen.

Beach Buggy Racing 2 now runs at 60 FPS

The 0.7.0 release adds Beach Buggy Racing 2 to the developer's supported-game notes and reports it running at 60 FPS. As with earlier compatibility claims, this is a specific tested workload and should not be interpreted as universal Android-game compatibility.

Should 0.6.1 users update?

If you are testing Husk on iOS 26 or newer, 0.7.0 is the more interesting build because it adds the built-in StikJIT workflow and the broader network changes while retaining the Android runtime direction introduced in the 0.6.x releases. Users who already have StikDebug working can keep that method; the new Automatic picker is designed to preserve existing StikDebug setups when it is installed.

Because this remains an experimental Android runtime, keep expectations app-specific. The merged built-in-JIT contribution was still new enough that its original pull request explicitly called the pairing/JIT path early-stage work. Back up anything important and expect some apps or games to need additional compatibility fixes.
